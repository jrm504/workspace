## 1. PHP2Shell (CVE-2026-109618, CVE-2026-109619)

- **Timeline:** Details leaked 20 Oct; emergency patch released 21 Oct 2026
- **Type:** Unauthenticated Remote Code Execution (RCE), CVSS v4.0 9.2
- **Simple description:** Two memory-handling flaws in the PHP core let an attacker run commands on a server with a specially crafted web request. Because the bug is in PHP itself, even websites with no bugs of their own are affected. The flaws had existed for about 14 years and were found with the help of AI tools.
- **What happened:** Details leaked before the planned disclosure, exploitation started before patches were available, and many government websites in Europe and elsewhere were temporarily taken offline.
- **Fixed versions:** PHP 8.5.12, 8.4.27, 8.3.36, 8.2.35 (with backports for 7.4, 8.0, 8.1).
- **Lessons:** Inventory everywhere PHP runs (hosting, NAS, control panels); have a "patch or disconnect" plan ready; a WAF is only a temporary layer.

## 2. OpenCode Console breach (16–17 Oct 2026)

- **Type:** Breach of a legacy system; exposure of third-party API keys
- **Simple description:** Attackers got into an older system behind OpenCode Console (a service that stores OpenAI/Anthropic/Google keys for whole teams), affecting about 1.4% of Console users. Some users were charged more than USD 1,700 in unauthorized usage overnight. OpenCode called it a "distillation attack"; some observers doubt that framing and see it as an ordinary breach.
- **Scope:** Console only, not the locally run OpenCode application.
- **Response:** Anthropic and Google blocked keys believed to be exposed; OpenAI worked with OpenCode on refunds.
- **Lessons:** Use dedicated, restricted keys with spending limits for intermediary services; revoke keys at the original provider, not just in the tool; shut down or clean up legacy systems.

## 3. OpenCode RCE via MCP OAuth (Pillar Security, disclosed 19 Oct 2026)

- **Type:** RCE on Windows/WSL, versions 1.0.137–1.18.32
- **Simple description:** Simply connecting the coding agent to a malicious remote MCP server can let it run commands on the developer's machine during the OAuth login, with no malicious software to install and no prompt injection needed.
- **Notable point:** The vendor fixed it in 1.18.33 (28 Sep) but issued no CVE and published no advisory, so users could not easily tell whether they were at risk.
- **Lessons:** Treat remote MCP servers as untrusted code; keep agents updated; expect vendors to publish transparent advisories.

## 4. OpenCode RCE via upgrade endpoint (GHSA-632h-h47v-g4x4)

- **Type:** RCE from a malicious web page (cross-origin), versions 1.14.30–1.18.21 installed via npm/pnpm/Bun
- **Simple description:** If a user running a vulnerable OpenCode opens a malicious web page, that page can trigger the upgrade mechanism and run an install script on the machine.
- **Fixed version:** 1.18.22 (24 Aug 2026).
- **Lessons:** Local HTTP services in developer tools are a real attack surface; enforce Origin/CORS checks and authentication even on localhost.

## 5. OpenCode unauthenticated HTTP server (CVE-2026-22812)

- **Type:** RCE, fixed in 1.0.216
- **Simple description:** OpenCode automatically started an HTTP server with no authentication, so any local process (or any website, when CORS is permissive) could run shell commands with the user's privileges.
- **Lessons:** Local services need authentication by default; run agents in a container/sandbox with least privilege.

## 6. LiteLLM malicious release (20–21 Oct 2026)

- **Type:** Supply chain attack (PyPI, Docker Hub, GHCR)
- **Simple description:** Attackers bypassed several security controls to publish a LiteLLM release containing a credential stealer (cloud credentials, passwords, AI service accounts) and a backdoor. A GitHub token leak in AI gateway logs is suspected.
- **Lessons:** Pin versions and verify hashes; rotate all secrets if you installed an affected release; keep tokens out of logs.

## 7. eMudhra / emSign private key exposure (from 18 Oct 2026)

- **Type:** PKI infrastructure compromise
- **Simple description:** An Indian certificate authority reported that private keys were exposed, which could let attackers issue fake certificates and impersonate legitimate websites. Some intermediate CAs are affected.
- **Lessons:** Watch for browser/OS announcements about distrusting CAs; use Certificate Transparency to monitor certificates issued for your domains.

## 8. ConnectWise Cloud Backup

- **Type:** Abuse of application identity in Microsoft 365
- **Simple description:** A compromised credential let attackers sign in as the application itself and access at least 173 customer M365 tenants. ConnectWise shut the service down.
- **Lessons:** Review enterprise app permissions and consents in your tenant; limit broad permissions granted to third-party apps.

## 9. Arista VeloCloud Orchestrator (CVE-2026-114625, CVSS 9.9)

- **Type:** SQL injection, zero-day exploited in the wild
- **Simple description:** An authenticated user can escalate to operator privileges through a SQL injection flaw in the on-prem SD-WAN management system.
- **Lessons:** Network management systems should be isolated and patched first, because taking one over means taking over the whole network.

## 10. GitLab Regular Expression Compiler (CVE-2026-85706)

- **Type:** Maximum-severity RCE; added by CISA to its known exploited vulnerabilities list
- **Simple description:** A flaw in the regex compiler allows remote code execution on GitLab servers; CISA ordered federal agencies to patch within 3 days.
- **Lessons:** Follow the CISA KEV catalog; self-hosted GitLab needs a fast patching process.

## 11. Node.js Brotli decoder (CVE-2026-111497)

- **Type:** Out-of-bounds write, can lead to RCE
- **Simple description:** Decoding attacker-controlled Brotli data can corrupt memory. The fix is part of the 21 Oct update for the 22.x, 24.x and 26.x lines (10 flaws in total).
- **Lessons:** Update runtimes regularly; take care with compression/decompression libraries that process untrusted input.

## 12. Portainer (two flaws, CVSS 9.4)

- **Type:** Privilege escalation, Docker host takeover
- **Simple description:** Ordinary users can mount host resources and take over the machine running Docker.
- **Lessons:** Container admin rights are effectively root on the host; separate privileges strictly.

## 13. Siemens Software Center (CVE-2026-110936)

- **Type:** DLL side-loading, exploited in the wild
- **Simple description:** Attackers pair a genuine, signed copy of the application with DLL files they supply; the application loads DLLs from its own folder without validating them. Fixed in 4.0.9.8.
- **Lessons:** A valid signature on the main file does not guarantee the files shipped alongside it are safe.

## 14. Railway

- **Type:** Incident exposing customers' environment variables
- **Simple description:** The deployment platform paused all deployments after confirming that customers' environment variables had been exposed.
- **Lessons:** Environment variables often hold secrets; rotate them after a PaaS incident and use a secret manager.

## 15. DNS Root KSK Rollover (11 Oct 2026)

- **Timeline:** 11 Oct 2026 (impact clearest on 11–13 Oct; failures can persist on resolvers that have not been fixed)
- **Type:** Operational event (not a vulnerability or an attack). ICANN/IANA changed the DNSSEC signing key of the root zone from KSK-2017 (Key Tag 20326) to KSK-2024 (Key Tag 38696).
- **Simple description:** From 11 Oct, only KSK-2024 signs the DNS root key set. A resolver that has DNSSEC validation enabled but does not trust the new key (Key Tag 38696 missing from its trust anchors) cannot validate and returns SERVFAIL, so users behind it may be unable to resolve many domains. Resolvers with DNSSEC validation turned off are not affected.
- **Why it is easy to miss:** KSK-2024 was published in the root zone on 11 Jan 2025, and most resolvers on current software picked it up automatically via RFC 5011 (ICANN reported over 95% of reporting resolvers had adopted it). The rest are older resolvers, ones with automatic updates disabled, ones without write access to the trust anchor directory, or ones configured manually.
- **Vietnam angle:** Advisories in Vietnam stress that DNS resolvers with DNSSEC validation enabled (ISPs, enterprises, government bodies) must check their trust anchors. This is an operational issue on the resolver side, not a fault of the .vn registry or registrars, which is why registrars rarely announce anything about it.
- **How to check:**
  - Look for `38696` in the trust anchor file (Unbound/PowerDNS: `root.key`; Knot Resolver: `root.keys`; BIND: `keyid 38696` should show as "trusted").
  - Run the RFC 8509 sentinel test (for example Cloudflare's dnstest.dev/ksk-2024 page).
  - Compare `dig domain.vn` with `dig domain.vn +cd`: if the `+cd` query works but the normal one returns SERVFAIL, it is very likely a validation failure.
- **How to fix:** Upgrade the resolver software, add the KSK-2024 trust anchor manually, or temporarily disable DNSSEC validation as an emergency measure. Because KSK-2017 no longer signs, a resolver that only knows the old key cannot learn the new one by itself.
- **What comes next:** In early 2027, KSK-2017 will be revoked and removed from the root zone. ICANN has also proposed moving from RSA to ECDSA P-256 over 2027–2030.
- **Lessons:** For scheduled infrastructure changes, verify automatic-update configuration before the change date and do not assume automatic updates worked. Failures can appear late because of caching, because backup resolvers mask the problem, or when systems restart later, so keep monitoring the SERVFAIL rate for several days after the key change.

### 15.1. Why did notices go out before 11 Oct, yet problems still show up around 21–22 Oct?

> Note: public sources explain the general mechanisms behind "delayed failures". There is no confirmed evidence of the specific cause in any given Vietnamese case on 21–22 Oct, so this section lists possibilities to check, not conclusions.

**Timeline**

| Date | Event |
|------|-------|
| 11 Jan 2025 | KSK-2024 published in the root zone alongside KSK-2017 |
| ~10 Feb 2025 | Auto-updating resolvers (RFC 5011) finish the 30-day wait and start trusting KSK-2024 |
| 27 Jul 2026, 1 Oct 2026 | ICANN repeats the deadline and how to check for Key Tag 38696 |
| 11 Oct 2026 | Root key set signed only by KSK-2024 |
| 11–13 Oct 2026 | Cached copies of the old key set (48-hour TTL) expire; resolvers lacking KSK-2024 start failing |
| 21–22 Oct 2026 | Failures may still appear on resolvers in the situations below |

**Reasons failures can appear later than the notices**

1. **Caching hides the failure temporarily.** The root key set has a 48-hour TTL. A resolver that cached the old copy just before 11 Oct keeps working until the cache expires. Busy resolvers fail sooner. Low-traffic resolvers, such as one serving a single machine or a small network, can take hours to days longer.
2. **Multiple resolvers mask the failure.** A client with one good and one broken resolver retries the good one, only more slowly. The failure shows only when the good resolver has a problem or its configuration changes.
3. **Automatic key updates (RFC 5011) are lost on restart or redeploy.** The mechanism needs the resolver to run continuously for 30 days and to write the learned key to disk. A resolver in a container with a read-only filesystem, or one rebuilt from an old image, reverts to the trust anchor baked into the image and restarts the 30-day clock. Failures can therefore show up during maintenance, reboots, upgrades, hardware swaps or new deployments after 11 Oct.
4. **Fresh installs within 30 days of the key change.** A new install has an outdated trust anchor and has no time to learn the new key. SERVFAIL reports of this kind appeared on router firmware (12 Oct).
5. **Symptoms look like other problems.** A failing resolver returns SERVFAIL, which looks like a broken website, flaky network or an ordinary DNS fault, so operations teams may take days to connect it to the key change. ICANN also said it is impossible to predict when affected operators will notice.
6. **A notice is not an action.** Notices went out months ahead, but most checks only happen after something breaks, especially in organizations without a dedicated DNS team.
7. **Noise from other events (speculation).** 21–22 Oct also saw PHP2Shell and many other incidents at once, so access problems could be misattributed. This is only a possibility and needs log verification.

**How to pin down the real cause when you see errors on 21–22 Oct**

- Check whether the resolver has Key Tag 38696, and record the software version and when the resolver was last restarted or redeployed.
- If `dig domain +cd` works but the query without `+cd` returns SERVFAIL, it is very likely a DNSSEC validation failure.
- If `+cd` also returns SERVFAIL, the cause is not DNSSEC validation (it could be authoritative DNS, the network or another service).
- SERVFAIL can be cached for up to 5 minutes, so wait after applying a fix before re-testing.
- Compare several networks/ISPs: if only some networks fail, a local resolver is the likely culprit.

## Recurring Patterns

- **AI finds bugs faster:** the time from disclosure to exploitation keeps shrinking (PHP2Shell).
- **AI developer tools are a new target:** OpenCode, LiteLLM, MCP servers.
- **Credential exposure causes direct damage:** API keys, GitHub tokens, app identities.
- **Forgotten local/legacy services:** unauthenticated HTTP servers, the old system behind Console.
- **Not every incident is an attack:** the root DNSSEC key change was scheduled; the risk lay in configurations that were never updated.
- **Vendor transparency matters:** silent patching leaves users unsure whether they are at risk.

## Quick Response Checklist

1. Inventory assets and the versions running.
2. Patch or isolate internet-facing systems.
3. Rotate secrets/API keys if exposure is suspected (revoke at the original provider).
4. Look for signs of compromise: unusual processes, unexpected outbound connections, configuration changes.
5. Follow official advisories and the CISA KEV catalog.
